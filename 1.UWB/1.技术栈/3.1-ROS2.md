# ROS2 串口通信、协议解析与 UWB 定位

> 基于 ROS2 开发串口通信节点，实现数据组帧、协议解析及三边定位解算，并发布 UWB、IMU 话题，完成嵌入式下位机与 ROS2 上位机通信。


## 1. 这项工作在系统中负责什么

- **下位机采集与输出**：STM32 控制 DW1000 完成测距，并按配置读取 IMU，通过串口输出文本协议帧。
- **上位机串口接入**：ROS2 节点读取串口字节流，处理一次读取不等于一条完整消息的问题。
- **数据转换**：把协议字符串转换为距离、加速度、角速度等结构化数据。
- **定位计算**：利用已知基站坐标和标签到基站的距离，计算标签位置。
- **ROS2 接口**：发布 UWB 和 IMU 消息，使后续可视化、融合节点等不必直接操作串口。

```text
STM32 / UWB 模块输出串口文本
    ↓
SerialDriver：读取已有字节
    ↓
FrameAssembler：缓存半帧，提取完整帧
    ↓
UwbProtocolParser：识别 mc / MP / mi，更新传感器状态
    ↓
LocationSolver → GetLocation：利用距离计算位置
    ↓
UwbLocationNode：组装 ROS2 消息
    ├─ /uwb/data：UWB 位置、距离
    └─ /imu/data：加速度、角速度
```

当前串口节点主要实现下位机到上位机的接收与发布链路。虽然串口以读写方式打开，但驱动没有提供业务命令发送接口，不能把这段代码描述成已经实现完整的双向命令控制。

## 2. 分点一：开发 ROS2 串口通信节点

### 2.1 工程与节点信息

| 项目 | 实际实现 |
| --- | --- |
| ROS2 包名 | `uwb_location` |
| 语言与构建 | C++17、`ament_cmake`、`rclcpp` |
| 可执行文件 | `uwb_location_node` |
| 节点名称 | `uwb_imu_node` |
| 串口参数 | `port`，默认 `/dev/ttyUSB0` |
| 波特率参数 | `baudrate`，默认 `115200` |
| 串口格式 | 8 位数据、无校验、1 位停止位，无硬件流控 |
| 轮询方式 | 5 ms ROS2 wall timer 调用 `pollSerial()` |
| 单次读取上限 | 1024 字节 |

可执行文件名与 ROS2 节点名不同：前者用于启动程序，后者由 `Node("uwb_imu_node")` 指定。



### 2.2 串口驱动如何工作

使用 Linux/POSIX 接口，不依赖 ROS 的 `serial` 包：

1. `open()` 以 `O_RDWR | O_NOCTTY | O_NONBLOCK` 打开设备。
2. 通过 `termios` 设置 raw 模式、波特率及 8N1。
3. 使用 `ioctl(FIONREAD)` 查询已有字节数量。
4. 用 `read()` 读取最多 1024 字节，返回 `std::vector<uint8_t>`。
5. 析构或关闭时释放文件描述符。

`O_NONBLOCK` 表示非阻塞打开，不能把传给驱动的 `11` 直接解释成“每次读取严格等待 11 ms”。源码的 `VTIME` 按十分之一秒单位设置，而该接收路径主要依赖非阻塞读取和已有字节查询。

**5 ms 是轮询周期，理论轮询频率约 200 Hz，不是 UWB 或 IMU 的保证发布频率。** 没有数据时直接返回；一次读取含多帧时，会连续处理和发布多次。

### 2.3 分层设计的价值

| 层 | 类/模块 | 职责 |
| --- | --- | --- |
| 驱动层 | `SerialDriver` | 打开、读取、关闭串口 |
| 组帧层 | `FrameAssembler` | 字节流到完整文本帧 |
| 解析层 | `UwbProtocolParser` | 文本帧到传感器状态 |
| 算法层 | `LocationSolver`、`trilateration` | 距离与基站坐标到位置 |
| 节点层 | `UwbLocationNode` | 参数、定时器、调用顺序和话题发布 |

串口、组帧、解析和定位模块没有直接绑定到 ROS2 消息发布逻辑，便于分别修改和验证。例如更换串口库时，可以保留协议解析器。

## 3. 分点二：实现字节流组帧，处理拆包和粘包

规则：

- 空闲状态遇到 `m` 或 `M`，开始接收一帧。
- 使用成员变量 `frame_` 和 `receiving_` 保存跨次调用的状态。
- 遇到换行符 `\n`，输出完整帧，帧中保留换行符。
- 一次输入可以提取多帧，返回 `std::vector<std::string>`。
- 未进入接收状态的其他字节会被忽略。
- 缓冲上限为 1024 字节；内容超限时清空当前缓存，返回等待帧头状态。

### 3.1 半帧跨次接收

```text
第 1 次读取：mi,部分字段
             → 尚无换行，保存到 frame_

第 2 次读取：剩余字段\r\n
             → 接在上次缓存后，输出完整帧
```

### 3.2 一次收到多帧

```text
一次读取：mc ...\r\nmi,...\r\n
              ↓
输出帧列表：[mc 帧，mi 帧]
              ↓
pollSerial() 逐帧解析
```

这解决了串口读取边界与应用帧边界不同的问题。ROS2 上位机按照文本协议的换行符判断边界，不依赖 STM32 的 IDLE 中断。

当前组帧器不做 CRC，也没有半帧超时机制。接收过程中遇到新的 `m/M` 不会立即重同步，因此“实现拆包、粘包处理”不等于已经覆盖所有乱码、丢字节和失步恢复场景。

## 4. 分点三：解析 UWB 与 IMU 文本协议

 `parseFrame()`，根据前两个字符选择协议分支。

| 帧类型 | 接受条件 | 当前提取的数据 |
| --- | --- | --- |
| `mc` | 完整字符串长度为 70 或 106，且 `sscanf()` 字段数符合预期 | 4 路或 8 路距离 |
| `MP` | CSV 至少 8 个字段 | 第 5 个字段转成直接距离，除以 100 后保存 |
| `mi` | CSV 字段数为 13、17 或 23 | 4 路或 8 路距离，以及三轴加速度、三轴角速度 |

### 4.1 mc：十六进制距离帧

- 通过 `sscanf()` 的 `%x` 读取距离和其他整数。
- 70 字节格式要求成功读取 11 个字段；106 字节格式要求 15 个字段。
- 距离保存到 `ranges_mm`，作为毫米值传给定位器。
- `mask`、序号、角色、标签 ID 等虽然被读取，但没有用于多标签状态分离和有效位判断。

这里的长度是组帧器输出的整个字符串长度，包含保留的行结束字符。改变下位机字段宽度或回车换行格式，可能导致长度检查不通过。

### 4.2 mi：距离与 IMU 混合帧

- 13 字段分支：从索引 2 开始读取 4 个距离，从索引 6 和 9 开始分别读取加速度、角速度。
- 17、23 字段分支：从索引 2 开始读取 8 个距离，从索引 10 和 13 开始分别读取加速度、角速度。
- 距离字符串按米读取，乘 1000 后保存为整数毫米。
- 距离字段为字面字符串 `NULL` 时，保存为 `-1`，定位时不作为有效距离。
- 加速度和角速度直接按浮点数读取，ROS2 解析器中没有再次进行单位转换。

即使收到 23 字段的帧，当前实现也只提取距离、加速度和角速度，没有将后面的磁场或姿态字段完整发布。

### 4.3 MP：直接距离分支

`parseMpFrame()` 将索引 4 的字段用 `atoi()` 转成整数，再除以 `100.0f`，写入 `direct_distance_m`，同时设置 `has_direct_distance = true`。

当前分支没有解析出标签的三维坐标，也没有更新基站距离数组。节点却仍在该帧解析成功后调用定位器，因此可能用到此前缓存的距离。不能把该分支笼统描述为“读取下位机已计算的位置”。

### 4.4 解析结果与状态缓存

解析器返回三种状态：

- `kParsed`：节点进行定位并发布消息。
- `kMalformed`：节点输出节流警告，同类日志间隔约 2 秒。
- `kIgnored`：不支持的帧类型，跳过。

统一缓存 `UwbSensorState` 包含 8 路距离、直接距离及其标志、IMU 数据及其标志。当前是单份缓存，没有按标签 ID 分组；未被本帧覆盖的字段会保留旧值。

CSV 拆分使用 `strtok()`，数值转换使用 `atoi()/atof()`。当前具有字段数和部分长度检查，但还没有严格的数值合法性、空字段保持和完整尾部检查，不能将它描述为完善的协议校验。

## 5. 分点四：接入三边定位解算

### 5.1 定位输入与基本原理

已知基站坐标 `(xi, yi, zi)` 和标签到该基站的距离 `ri`，标签位置 `(x, y, z)` 满足球面约束：

```text
(x - xi)^2 + (y - yi)^2 + (z - zi)^2 = ri^2
```

程序利用多组距离约束求交点或选取候选解。三维空间中三个球面可能对应两个镜像交点，不能仅因为“有三个距离”就宣称任意场景下都有唯一三维位置。

本项目调用链：

```text
LocationSolver::solve(ranges_mm)
    → GetLocation(best_solution, anchors, ranges)
    → deca_3dlocate(...)
    → trilateration(...)
    → 返回位置与状态码
```

### 5.2 距离筛选和基站选择

`GetLocation()` 的实际处理：

1. 扫描最多 8 路距离，只有大于 0 的值才被视为有效。
2. 少于 3 个有效距离，返回失败。
3. 3 个有效距离，采用三基站路径。
4. 4 个有效距离，采用四基站路径。
5. 多于 4 个时，按距离排序并优先选取最近的 4 个。
6. 将毫米距离除以 1000，转换为米后计算。

因此“支持最多 8 个基站距离输入”不表示“同时对 8 个基站做统一最小二乘优化”。源码还存在更换基站组合的重试分支，但其触发条件为 `result == 0`，不能直接认为所有失败都会自动重试。

三基站候选解的选择包含“标签位于基站下方”的假设。实际安装布局需要与该假设相符。

### 5.3 当前基站坐标

写死了以下坐标，单位按算法使用为米：

| 基站 | x | y | z |
| --- | --- | --- | --- |
| A0 | 0 | 0 | 2.5 |
| A1 | 0 | 1 | 2.5 |
| A2 | 1 | 0 | 2.5 |
| A3 | 1 | 1 | 2.5 |
| A4 | 2 | 1 | 2.5 |
| A5 | 2 | 0 | 2.5 |
| A6 | 3 | 1 | 2.5 |
| A7 | 3 | 0 | 2.5 |

这些是当前代码配置，不是从现场自动测量得到的值。类提供了 `setAnchors()`，但串口节点没有将基站坐标声明为 ROS2 参数；更换场地时需要更新配置或补充参数入口。

## 6. 分点五：发布 UWB 和 IMU 话题

### 6.1 话题与消息类型

| 话题 | 类型 | 发布内容 |
| --- | --- | --- |
| `/uwb/data` | `uwb_location/msg/Uwb` | 时间戳、x/y/z、distance、d0～d5 |
| `imu/data` | `sensor_msgs/msg/Imu` | 时间戳、加速度、角速度，以及固定姿态值 |

代码中的 `imu/data` 是相对名称，在默认根命名空间下解析为 `/imu/data`；`/uwb/data` 是绝对名称。加命名空间运行时，两者的命名行为不同。

两者均以队列深度 1000 创建。每次成功解析一帧，`publishData()` 使用同一次 `now()` 为两个消息填时间戳；这是上位机发布时刻，不是下位机传感器采样时刻。

### 6.2 UWB 消息字段与单位

自定义消息位于 [Uwb.msg](../6.ROS2/src/uwb_location/msg/Uwb.msg)：

```text
std_msgs/Header header
float32 x
float32 y
float32 z
float32 distance
float32 d0
float32 d1
float32 d2
float32 d3
float32 d4
float32 d5
```

- `x/y/z`：定位器计算结果，按当前坐标和距离转换使用米。
- `d0～d5`：直接复制 `ranges_mm`，当前实际保存的是毫米，并未统一换算成米。
- `distance`：若 `has_direct_distance` 为真，使用米制的 `direct_distance_m`；否则使用毫米制的 `ranges_mm[0]`，当前存在单位不一致问题。
- 状态中最多有 8 路距离，但消息只定义了 6 路，A6、A7 距离没有单独发布字段。
- UWB 消息没有填写 `header.frame_id`，也没有携带定位状态码或标签 ID。

### 6.3 IMU 消息的实际内容

- `header.frame_id = "base_link"`。
- 三轴加速度填入 `linear_acceleration`。
- 三轴角速度填入 `angular_velocity`。
- `orientation.w = 1.0`，其他分量默认 0，即固定单位四元数。
- 没有填写经过标定的协方差，也没有使用解析器中的 `has_imu` 决定是否发布。

因此当前实现完成了加速度和角速度的 ROS2 消息映射，**没有发布真实解算姿态**。只收到 `mc` 或 `MP` 时，也会发布默认或此前缓存的 IMU 数据。下游应注意数据新鲜度，后续应按有效标志发布并明确姿态不可用状态。

## 7. 串起一次完整的数据处理过程

以一条有效 `mi` 帧为例：

1. STM32 输出包含距离、加速度和角速度的文本帧。
2. 5 ms 定时回调读取串口已有数据，最多取 1024 字节。
3. 组帧器找到帧头，跨读取保存内容，遇到换行后交付完整帧。
4. 解析器检查字段数，将距离换为毫米，并更新 IMU 缓存。
5. 定位器筛选有效距离，选取基站，转换为米并调用三边定位函数。
6. 节点组装 UWB 和 IMU 消息，并发布给 ROS2 订阅者。

这条链路把下位机自定义串口协议转换成上位机可订阅的数据接口。后续节点不必重复处理串口、拆包和文本字段。
